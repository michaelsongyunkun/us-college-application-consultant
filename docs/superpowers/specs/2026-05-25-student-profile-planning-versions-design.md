# 学生档案、多份规划与版本历史设计

## 目标

将当前一次性、本地草稿式的规划编辑流程升级为登录账号下可持续维护的规划工作区：

- 每个家庭账号维护一份学生基础档案。
- 同一学生可以建立多份彼此独立的规划方案。
- 每份方案保存一个持续更新的当前稿，并支持手动创建不可变版本快照。
- 版本快照可查看与恢复，恢复不会删除或覆盖历史记录。
- 原有 Agent 生成、推荐结果与 JSON / Word 导出继续围绕当前选中的方案工作。

## 已确认的产品边界

- 账号模式：首版一个登录账号对应一个学生 / 家庭，不支持顾问账号同时管理多个学生。
- 多份规划：同一学生可同时维护多份独立方案，例如不同专业主线或不同申请策略。
- 档案共享：基础学生档案全局共用，各规划引用最新档案；快照中保存当时完整档案数据以便追溯。
- 版本产生方式：普通保存只覆盖当前稿；用户点击“创建版本快照”时才生成历史版本。
- 版本恢复方式：从历史快照恢复会将内容写入当前稿，快照本身仍保留。

## 当前项目背景

当前应用已具备：

- SQLite 用户、会话、密码重置及后台统计能力。
- 登录后的主页面规划表格、推荐结果与导出流程。
- 用户隔离的浏览器本地草稿兼容存储。

当前没有：

- 服务端持久化的学生档案。
- 同一账号下的多规划管理能力。
- 当前稿服务端保存和快照历史。

本功能沿用现有原生 Node HTTP 服务与 SQLite，不引入新框架，也不改变固定 Agent 提示词。

## 页面信息架构

主页面在现有工作区上增加三部分管理能力：

### 学生档案摘要

位于规划编辑区上方，展示学生核心背景摘要，例如年级、目标专业方向和最近更新时间，并提供“编辑学生档案”操作。

档案编辑沿用当前背景输入字段：

- 年级
- 专业方向
- 核心能力 / 特长
- 可利用资源
- 性格 / 行为倾向
- 兴趣方向
- 现有课外活动

这些字段从当前规划草稿中提升为账号级学生档案。规划生成与推荐逻辑仍可通过同样的 `profile` 对象消费它们。

### 规划方案选择器

位于编辑区左侧或顶部窄栏，支持：

- 列出当前账号的所有规划方案。
- 新建规划，并要求输入方案名称。
- 切换当前规划。
- 重命名当前规划。
- 删除非最后一份规划；删除前明确确认。

新账号首次进入且没有规划时，系统自动建立一份名为“默认规划”的空方案，避免出现无可编辑对象的状态。

### 版本历史

位于当前规划旁的侧栏或折叠区域，支持：

- 显示当前方案的快照列表，按创建时间倒序排列。
- 创建快照时输入可选备注，例如“首次成稿”或“夏校筛选后调整”。
- 查看快照的创建时间与备注。
- 将选定快照恢复到当前稿。

首版不提供快照编辑或删除，避免历史证据被误改。

## 数据模型

所有新增数据均存入当前 `auth.sqlite` 数据库，并由登录用户所有权隔离。

### `student_profiles`

每个用户最多一条学生档案记录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 档案 ID |
| `user_id` | INTEGER UNIQUE FK | 所属用户 |
| `profile_json` | TEXT NOT NULL | 与现有 `profile` 对象兼容的 JSON |
| `created_at` | TEXT NOT NULL | 创建时间 |
| `updated_at` | TEXT NOT NULL | 最近更新时间 |

### `planning_projects`

每个用户可拥有多条规划方案。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 方案 ID |
| `user_id` | INTEGER FK | 所属用户 |
| `name` | TEXT NOT NULL | 方案名称 |
| `current_draft_json` | TEXT NOT NULL | 当前稿 JSON |
| `created_at` | TEXT NOT NULL | 创建时间 |
| `updated_at` | TEXT NOT NULL | 最近保存时间 |

`current_draft_json` 保存现有规划页面中除全局档案以外的可恢复内容：

- `activities`
- `rawAnswer`
- `narrative`
- `futureLearningDirection`
- `competitionRecommendations`
- `summerSchoolRecommendations`
- `recommendationLetterStrategy`
- `caseMatches`

### `planning_snapshots`

每次手动创建版本时新增一条不可变快照。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 快照 ID |
| `project_id` | INTEGER FK | 所属规划方案 |
| `user_id` | INTEGER FK | 所属用户，用于直接验证访问边界 |
| `note` | TEXT NOT NULL | 用户备注，可为空字符串 |
| `snapshot_json` | TEXT NOT NULL | 快照完整内容 JSON |
| `created_at` | TEXT NOT NULL | 创建时间 |

`snapshot_json` 同时保存：

- 当前 `profile`
- 当前方案名称
- 当前方案的完整规划稿内容

因此即使之后全局档案被更新，历史报告仍能准确还原创建快照时的背景。

## 服务模块

新增 `planning-service.mjs`，避免继续扩大认证模块职责。它接收现有 `authDb`，提供：

- 获取或更新当前用户学生档案。
- 列出、新建、读取、保存、重命名和删除用户自己的规划。
- 创建、列出和恢复当前用户自己的规划快照。
- 首次进入时确保默认规划存在。

`server.mjs` 负责路由、鉴权、JSON 输入输出与错误映射，不直接拼接规划数据 SQL。

## API 设计

所有以下接口均要求有效登录会话，且只能访问当前用户拥有的数据。

### `GET /api/student-profile`

返回当前用户的学生档案。首次不存在时返回空 `profile` 对象，而不是 `404`。

```json
{
  "profile": {},
  "updatedAt": null
}
```

### `PUT /api/student-profile`

保存当前用户的全局档案。

请求：

```json
{
  "profile": {
    "grade": "10年级",
    "majorDirection": "计算机 / AI"
  }
}
```

返回保存后的档案与更新时间。

### `GET /api/plans`

列出规划方案；如果用户没有方案，则自动建立并返回“默认规划”。

### `POST /api/plans`

创建空的规划方案。

请求：

```json
{ "name": "CS + 教育公益主线" }
```

方案名称去除首尾空格，不得为空，限制为 80 个字符。

### `GET /api/plans/:id`

返回指定方案的当前稿；不是当前用户拥有的方案统一返回 `404`。

### `PUT /api/plans/:id`

保存指定方案的当前稿和可选新名称，不创建快照。

### `DELETE /api/plans/:id`

删除指定方案及其快照；如果用户仅剩这一份方案，则拒绝删除并返回 `409`。

### `GET /api/plans/:id/snapshots`

返回指定方案的快照概要列表，不默认返回完整 `snapshot_json`。

### `POST /api/plans/:id/snapshots`

使用服务端当前存储的学生档案与该方案当前稿创建快照，避免由前端伪造历史内容。

请求：

```json
{ "note": "首次成稿" }
```

### `POST /api/plans/:id/snapshots/:snapshotId/restore`

恢复快照内容：

- 将快照中的规划稿复制到方案当前稿。
- 将快照中的学生档案复制回全局档案，使页面整体回到历史状态。
- 不创建额外快照，也不修改源快照。

返回恢复后的档案与当前规划内容。

## 前端数据流

### 初始化

1. 用户登录成功后加载学生档案与规划列表。
2. 系统选择最近更新的方案，或首次创建的“默认规划”。
3. 加载该方案当前稿，将 `profile` 和规划数据填入既有页面控件。
4. 仅在该用户服务端还没有任何已保存内容时，检测旧的按用户隔离本地草稿，并提供自动迁移到默认规划；迁移成功后清除本地草稿。

### 保存

- “保存当前规划”同时保存全局档案和选中方案当前稿。
- 保存成功后更新方案列表中的更新时间和状态提示。
- Agent 生成或解析 Codex 回答后沿用现有自动保存意图，保存到当前方案而非浏览器存储。

### 切换方案

- 若页面存在未保存修改，切换前提示用户保存或放弃修改。
- 切换后保留同一份全局档案，替换活动表格、叙事、推荐和导出上下文。

### 快照与恢复

- 创建快照前先保存当前档案与当前稿，确保快照内容对应页面可见状态。
- 恢复快照需要确认；恢复完成后页面加载快照中的档案和方案内容，并标记为当前已保存内容。

## 本地草稿迁移

目前修复后的前端使用按用户 ID 隔离的本地草稿。服务端规划功能上线后：

- 本地草稿不再作为日常主存储。
- 用户首次进入新功能时，如果服务端默认规划仍为空且存在本地草稿，则将其写入全局档案和默认规划当前稿。
- 若服务端已有内容，则不自动覆盖服务端数据，也不自动导入旧草稿。
- 成功导入后删除该用户对应的本地草稿记录。

## 权限与安全

- 所有档案、规划和快照 API 均必须经过 `requireUser`。
- 服务方法在每次读取或写入时同时匹配 `user_id`，避免仅凭前端传入 ID 访问他人数据。
- 对他人资源与不存在资源统一返回 `404`，不暴露是否存在。
- API 复用现有请求体大小限制与敏感写操作限流机制。
- 快照内容由服务端从当前已保存数据生成，保证历史不可由请求直接篡改。

## 错误与空状态

- 学生档案未填写：显示引导文案，允许先创建和编辑规划。
- 无方案：自动创建默认规划。
- 方案名称无效：页面显示内联错误，不创建记录。
- 删除最后一份方案：提示至少保留一份规划。
- 快照为空：显示“尚未创建版本快照”。
- 恢复失败或访问越权：保留当前可见内容并显示错误提示。

## 测试与验收

### 服务层测试

- 一个账号只能有一份学生档案，更新后可读取最新数据。
- 同一账号可创建两份规划，两份当前稿独立保存。
- 普通保存不会增加快照数量。
- 创建快照包含当时档案与规划当前稿。
- 更新档案和当前稿后恢复旧快照，二者均还原，且原快照仍存在。
- 用户 A 无法读取、更新、删除或恢复用户 B 的规划及快照。
- 无法删除最后一份规划。

### 路由测试

- 未登录请求新增 API 返回 `401`。
- 登录后可完成档案保存、创建规划、保存、创建快照和恢复流程。
- 访问他人规划 API 返回 `404`。

### 前端验证

- 首次登录可看到默认规划。
- 可新建并切换多份规划，内容不会串写。
- 点击保存只更新当前稿，不增加快照历史。
- 创建快照后可在历史中查看并恢复。
- JSON / Word 导出导出当前选中方案及当前档案状态。
- 旧本地草稿仅在服务端为空时迁移一次。

## 不包含范围

- 顾问账号管理多个学生。
- 多用户共享同一学生档案。
- 快照删除、编辑或版本差异对比。
- 活动任务时间线、截止日期提醒和证据附件。
- 资源数据核验后台及选校清单。

这些能力可以在本数据基础稳定后单独设计和实现。
